## 主要判斷

### 為何把這四件事放一起做

它們有強耦合：
- 寫 `kernel/rcu.md` 後，`MCUPM_Code_Review` Q5 的 ackdata race 才有「進階修法」可以指；
- 寫 `kernel/workqueue.md` 後，`MCUPM_Code_Review` Q10 / Q11 的 deprecated API 才有「主題對應頁」；
- 寫 `kernel/bitmap.md` 後，`google_code_review_semaphore_prep_linux_solution` 中 DSP IPI channel pool 的修法才有 standalone 章節可指；
- 五份檔都進入後，`_index.md` / `overview.md` 才能一次同步完，避免半同步狀態。

分批做的話會有兩三次「索引落後內容」的中間態，hygiene 成本反而更高。

### 為何選 RCU / bitmap / workqueue 三主題（而不只挑一個）

使用者明示「三個都寫」。從 leverage 看：
- **RCU**：是同步原語的最後一塊拼圖；spinlock 已寫，rwlock 已被 RCU 取代，剩 RCU 自己。
- **bitmap**：跨 patterns（bit-manipulation）與 kernel（cpumask、IRQ、SCMI），交叉引用價值高。
- **workqueue**：MCUPM driver 的 Q10 / Q11 直接需要這個主題；不寫它則 MCUPM 索引會懸空。

三者都有「服務既有 wiki 的具體交叉引用需求」，不是 academic completeness。

### MCUPM vs google-stack-with-min 的角色差異

兩份都是 code review 教材，但層次不同：
- **google-stack-with-min**：單檔 71 行 stack，5 個 bug，是 SKILL.md 指定的 reference 八件套——「教學者學寫教材」用。
- **MCUPM**：跨 3 檔 driver 的 11 題真實 production review——「面試者練 driver review」用。

wiki/interview 從原本「教材級 + 單主題速成」兩層，擴成「教材級 + 同步原語 + driver 級」三層。
